## 一、目标与结论

目标：GPU PC（RTX 4050 6GB + 15GB RAM）+ WSL（15GB RAM）跨机分层推理 Qwen3.6-27B 和 Qwen3.6-35B-A3B。

两个模型都是**混合架构**（Gated DeltaNet SSM × 3 + Full Attention × 1 循环），GGUF arch 分别为 `qwen35`（dense 65 层）和 `qwen35moe`（MoE 41 层，256 experts）。mistral.rs 原本都不支持。

结论：
- ✅ TCP 桥接机制在 27B 上端到端跑通（cuda 12 层 + 本机 cpu 37 层 + WSL remote 16 层，连续 decode ~2 t/s）
- ❌ qwen35/qwen35moe 的模型实现数值不正确（纯 CPU 单机 0.8B 小模型也输出乱码，llama.cpp 同模型输出正常）
- 下一步聚焦数值调试，见第五节

## 八、后续（2026-08-18）：数值问题已解决，双模型跑通

第五节嫌疑清单的最终答案——共 6 个数值/结构 bug（全部修复并验证）：

1. conv1d 核方向反了（w[0] 应乘最旧帧）
2. DeltaNet 递推：先衰减 S 再检索；读出应为 S^T @ q（收缩 key 维）
3. norm_gated eps 位置：`x * rsqrt(mean(x²)+eps)`（eps 在 sqrt 内）
4. SSM 状态被引擎 warmup 请求污染 → 新增 reset_recurrent_states()
5. **MTP 层被当主干层执行**（27B block_count=65=64+1 MTP，0.8B 无 MTP 恰好不触发）→ block_count 减 nextn_predict_layers
6. **SSM v 头 repeat 顺序**：GGUF 是 tiled 序（llama.cpp 转换器重排过），代码按 grouped 序 —— 0.8B 组头比 1:1 恰好不触发，27B 3:1 首发

调试方法论记录：0.8B 小模型纯 CPU 复现 + llama.cpp 逐层 dump 对照（工具在 /tmp/q35dump/，仓库外），24 层隐藏状态对齐到 <1%。

最终结果：

| 模型 | 拓扑 | 输出 | 性能 |
|------|------|------|------|
| Qwen3.6-27B Q3_K_M | 12 cuda + 37 cpu + 15 remote | ✅ 正确 | prompt 5.2 T/s, decode 2.42 T/s |
| Qwen3.6-35B-A3B Q3_K_M | 8 cuda + 17 cpu + 15 remote | ✅ 正确 | ~1 token/min（见下） |

35B 慢的原因与优化方向：MoE 256 experts 在 CPU 的 FusedMoe 前向（疑似未按 top-8 稀疏派发，或 Q3_K 逐次反量化开销）、SSM 逐 token 标量循环 prefill。下一步优化：expert 稀疏派发核查、SSM chunked prefill、SSM CUDA kernel。

日志：`logs/bridge_27b_SUCCESS_20260818.log`、`logs/bridge_35b_correct_slow_20260818.log`

## 九、后续（2026-08-18 晚）：35B 提速 ~200x；Qwen3.8-27B 跑通

### 9.1 35B 慢因实锤与稀疏 MoE 修复（mistral.rs `a9f7a8d3b`）

根因：candle 的 MoE 索引 GEMV 快速路径（`QTensor::indexed_gemv` → `repack::try_indexed_gemv`）**只有 aarch64 实现**，x86_64 直接返回 None；于是 `qtensor_indexed_moe_forward` 退化为**每次前向把全部 256 个 expert 的 Q3_K 权重反量化成 F32** 再 gather matmul——每个 token 每个 MoE 层反量化 ~380MB。

修复（`mistralrs-quant/src/gguf/cpu.rs`）：新增 `sparse_indexed_moe`——按 expert 切分堆叠 QTensor 的原始字节流（GGUF 同构张量等长均分），每个 (token, expert) 对只与它路由到的那个 expert 的量化权重做 matmul，不触碰其余 248 个 expert。单测：F32 权重与 dequantize+gather 参考逐位一致（<1e-5）；Q8_0 差异仅为 ggml 量化激活固有噪声。

实测（拓扑 8 cuda + 17 cpu + 15 remote）：decode **~3.4 T/s**（24651 tokens / 2h 超时杀），修复前 ~1 token/min，**提速约 200 倍**。

遗留问题：长输出退化——开头推理正常（先英文打草稿再成诗），约 4000 token 后陷入"风把落叶写成信笺"无限重复，未触发 EOS，2 小时 decode 2.4 万 token 最终把 GPU PC 跑到 OOM 重启。

**定位（2026-08-19 采样对照实验）**：用 `mistralrs serve`（8080 端口，API 可控采样参数，CLI `run` 不支持自定义 temperature）跑同 prompt 对照：
- temp=0.1 / top_p=0.1 / max_tokens=2000（与出问题时同参数）：✅ 输出正常，写完整首诗+赏析后自然 EOS 停止（FINISH: stop）
- temp=0.7 / top_p=0.9 / max_tokens=2000：（结果待补）

结论（暂定）：窄采样和稀疏 MoE 路径本身在 2000 token 内输出完全正确，排除"稀疏修复引入数值错误"；重复是**超长 decode（数万 token）下的长程退化**（SSM 状态漂移或 KV 累积），且无限 decode 会把 15GB GPU PC 跑 OOM。实操建议：生产使用务必设 max_tokens 上限。
